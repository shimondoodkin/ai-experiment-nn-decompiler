# Prior work covers the parts, not the pipeline

The closest prior work is **MIPS** (Michaud, Tegmark et al., 2024). It already automates "small trained ReLU network → Python program", rounds weights within 0.01 of an integer, prefers the shortest program, and reports 32 of 62 tasks solved against 30 for GPT-4 ([arXiv 2402.05110](https://arxiv.org/abs/2402.05110)). This repo therefore cannot claim novelty for automated decompilation of small nets or for integer snapping. Every other ingredient also has a precedent somewhere. Exact ReLU-to-tree conversion exists (Aytekin 2022, RENTT 2025). KAN symbolification snaps learned functions to closed forms and refits their constants. Cranmer et al. 2020 showed that symbolic distillations extrapolate better than the source network. Huang et al. (ICML 2026) decompile trained transformers into short RASP programs. What the literature search did not find is this repo's combination: an off-the-shelf LLM coding agent, blind to the task, reading a per-neuron code dump of a trained feed-forward MLP; snapping to *non-integer intended* constants such as 0.2 or bracket edges at 20 and 80; acceptance judged against the network itself; a deterministic tool distilled from the agent's notes and tested on held-out models; and a CPU speed comparison of branch code against straight-line MLP C. That combination can be claimed carefully as "not found in prior work we searched". The right baselines are PySR on network samples, sklearn tree distillation, exact activation-region decomposition, hand-unrolled straight-line C, and an LLM-from-input/output-only ablation. All five run on a CPU-only Windows laptop, with Python 3.13 friction noted below.

## MIPS already automates weights-to-Python with snapping

MIPS is the paper a reviewer will compare this repo against first, so its scope matters in detail. It trains the smallest RNN that solves a task. The RNN has the form h_i = f(h_{i−1}, x_i), y_i = g(h_i), where f and g are **ReLU MLPs with a linear final layer**. An AutoML binary search picks hidden sizes from 1 to 128, widths up to 256 and depths 1–3. Five normalizers are then applied in order: whitening, Jordan normal form, Toeplitz simplification, de-biasing, and **quantization that snaps any weight or bias within ε = 0.01 of an integer to that integer** ([arXiv HTML](https://arxiv.org/html/2402.05110v1)). Next, an "integer autoencoder" maps hidden states to bitstrings or to an integer lattice found by a GCD lattice finder, with settings chosen by minimum description length. Boolean or AI-Feynman-style brute-force symbolic regression then writes the transition and output functions into a Python template. The code is public at github.com/ejmichaud/neural-verification. The paper also appeared in *Entropy* in December 2024 ([PMC](https://www.ncbi.nlm.nih.gov/pmc/articles/PMC11727218/)).

The differences are real but narrow. MIPS works on **integer and bit sequence tasks**. Its programs are checked against benchmark test data. Only binary addition was formally verified, in Dafny with manual annotations. The paper lists two failure modes that sit close to this repo's territory: noise and nonlinearity breaking the lattice autoencoder on Diff_Abs_Values, and "continuous computation" breaking the finite-state assumption on Majority tasks ([arXiv HTML](https://arxiv.org/html/2402.05110v1)). MIPS also *co-designs* the network, shrinking it until extraction is easy. This repo decompiles a given feed-forward MLP over real-valued inputs, and its piecewise structure (|a−b|, median, brackets) comes out as conditionals and max/min, not as lattice formulas.

On the transformer side, the post-hoc analogue is **Huang, Bakalova, Bhattamishra, Merrill and Hahn, "Discovering Interpretable Algorithms by Decompiling Transformers to RASP"**. The arXiv comment says ICML 2026, although an ICLR 2026 listing with the same title also exists ([arXiv 2602.08857](https://arxiv.org/abs/2602.08857)). It rewrites a GPT-2-style transformer *exactly* into D-RASP, under a linearized-LayerNorm assumption. It then prunes causally irrelevant parts and swaps matrices and MLPs for library primitives. The pruned programs keep **more than 90% of model performance**, so they are approximate, not equivalent ([Neuroexplicit blog](https://www.neuroexplicit.org/blog/2026-06-10-decompiling-transformers/)). The pipeline shape (exact reparameterization, then simplification to a short program) matches this repo's. The architecture, the output language and the strictness of verification differ. Two other systems obtain programs by *changing the architecture* so that extraction is easy: **Learning Transformer Programs** (NeurIPS 2023) trains constrained transformers that convert to Python by construction ([NeurIPS](https://proceedings.neurips.cc/paper_files/paper/2023/hash/995f693b73050f90977ed2828202645c-Abstract.html)), and **Weights to Code** (2026) uses a Discrete Transformer and reports MIPS-comparable results ([arXiv 2601.05770](https://arxiv.org/abs/2601.05770)). Neural decompilers for Tracr reach about 30% exact and over 70% functionally equivalent programs, but only on *compiled*, not trained, weights ([arXiv 2410.00061](https://arxiv.org/html/2410.00061v1)).

The manual mechanistic-interpretability classics provide precedent and one warning. Nanda et al. recovered a Fourier "rotation around a circle" algorithm from small modular-addition transformers by hand ([arXiv 2301.05217](https://arxiv.org/abs/2301.05217)). **"The Clock and the Pizza"** showed that small changes to hyperparameters or seed make networks learn *different* algorithms for the same task ([NeurIPS 2023](https://proceedings.neurips.cc/paper_files/paper/2023/hash/56cbfbf49937a0873d451343ddc8c57d-Abstract.html)). For this repo, the lesson is that "matches the expected program" is the wrong success criterion. Equivalence to the network, which the repo's checker tests, is the right one. **Compact Proofs** (NeurIPS 2024) is the strongest precedent for verification. It turns reverse-engineered mechanisms into formal accuracy lower bounds for 151 small transformers, and names "compounding structureless noise" as the main obstacle ([arXiv 2406.11779](https://arxiv.org/abs/2406.11779v8)). ACDC outputs circuit subgraphs, not programs. It recovered 68 of roughly 32,000 edges of GPT-2's Greater-Than circuit ([arXiv 2304.14997](https://arxiv.org/abs/2304.14997)), so it is adjacent to the repo's dead-unit pruning, not to program emission.

## LLMs explain networks from behaviour, almost never from weights

Every LLM-based interpretability system found reads *behaviour*: activations, input/output probes or (x, y) samples. OpenAI's neuron explainer (2023) uses an explain, simulate and score loop that outputs natural language ([OpenAI](https://openaipublic.blob.core.windows.net/neuron-explainer/paper/index.html)). The **FIND benchmark with its Automated Interpretability Agent** (NeurIPS 2023 Datasets & Benchmarks) is the closest in task style. An off-the-shelf LM with black-box access writes code or language descriptions of procedurally built numeric and text functions. Its main failure is that descriptions capture global behaviour and miss local corruptions ([DeepAI listing](https://deepai.org/publication/a-function-interpretation-benchmark-for-evaluating-interpretability-methods); [MIT news](https://computing.mit.edu/news/ai-agents-help-explain-other-ai-systems/)). That failure is exactly the blurred-boundary detail a weight-level dump exposes. MAIA (ICML 2024) and InterpAgent (2026) extend the agent loop to vision models and sparse transformers, and still output prose ([MAIA](https://multimodal-interpretability.csail.mit.edu/maia); [arXiv 2605.01555](https://arxiv.org/html/2605.01555v1)). LLM-SR (ICLR 2025 oral) and LaSR (NeurIPS 2024) have LLMs propose equation programs fitted to data. Their constants are *fitted*, not snapped ([ICLR](https://proceedings.iclr.cc/paper_files/paper/2025/hash/28df8e730c054c5331855fd4d5403ba9-Abstract-Conference.html); [arXiv 2409.09359](https://arxiv.org/pdf/2409.09359)).

Only two lines let an LLM look inside a trained network. Harvey et al. (2025) show a vision LLM *plots* of a trained KAN's edge functions and ask it for formula ansätze. That requires the KAN architecture, and the LLM sees images, not code ([arXiv 2505.07956](https://arxiv.org/html/2505.07956v1)). **Weight Oracles** (NeurIPS 2026 workshop spotlight) fine-tunes language models to read raw weights of small transformers. It reaches 99% held-out forward-pass simulation accuracy and 0.93 AUROC on attention-routed backdoor detection ([arXiv 2610.07334](https://arxiv.org/abs/2610.07334v1)). It outputs simulations and diagnoses, not refactored programs, and its input encoding (text or embeddings) was not confirmed. The Jane Street "reverse engineer our network" puzzle was human-led, with an LLM writing only a reference md5 implementation ([Jane Street](https://blog.janestreet.com/can-you-reverse-engineer-our-neural-network/)).

The most useful data point is **MIPS's own GPT-4 Turbo baseline**. GPT-4 was given two length-10 input/output lists, asked for a formula and then Python, and allowed three attempts. It solved 30 tasks, MIPS solved 32, and MIPS solved 13 that GPT-4 missed ([ar5iv](https://ar5iv.labs.arxiv.org/html/2402.05110)). Each approach found things the other missed. This repo gives the LLM the weights *as code* and a checker. That sits between the two arms, and no published work was found that tests it.

## Exact ReLU-to-tree conversion is faithful but not short

That a ReLU MLP is exactly a piecewise-linear function, and so exactly an oblique decision tree, is old news. Nguyen et al. (2020) gave an exact-convertible decision tree ([arXiv 2003.04675](https://arxiv.org/abs/2003.04675)). **Aytekin's "Neural Networks are Decision Trees" (2022)** claims exact equivalence for any piecewise-linear network ([arXiv 2210.05189](https://arxiv.org/abs/2210.05189v1)). Chang et al. convert ReLU controllers to pruned exact trees and report verification speedups of up to 21× ([arXiv 2304.06049](https://arxiv.org/abs/2304.06049)). **RENTT** (2025) extends exact trees to CNNs and RNNs and has runnable research code ([arXiv 2511.09299](https://arxiv.org/html/2511.09299); [GitHub](https://github.com/HelenaM23/RENTT)). Their node tests are the network's own neuron sign tests, and their leaves are affine maps. The result is faithful but grows with the number of regions, and it is not a short program with intended constants. Orfanos and Lelis (2023) come closest to "ReLU net → short if-then-else program", using the oblique-tree view to synthesize programmatic RL policies. No code was found ([arXiv 2308.02729](https://arxiv.org/abs/2308.02729)).

Region enumeration is cheap in low dimension. **Hanin and Rolnick (NeurIPS 2019)** show that the average number of activation patterns is bounded by (total neurons)^(input dimension), independent of depth ([NeurIPS](https://proceedings.neurips.cc/paper/2019/hash/9766527f2b5d3e95d4a733fcfb77bd7e-Abstract.html)). For 1–3 inputs and a few dozen neurons, a full region list is small. For 9-input models (such as the Game of Life cell rule in the design) the bound is loose, so enumeration needs a budget. **parx** (`pip install parx`, MIT, alpha) enumerates exact regions with H-representations and per-region affine maps for Linear→ReLU stacks. It needs Julia 1.10+ ([GitHub](https://github.com/Johanmkr/parx)). SplineCam (CVPR 2023) computes regions exactly, but only on 2-D slices, and depends on graph-tool ([CVF](https://openaccess.thecvf.com/content/CVPR2023/html/Humayun_SplineCam_Exact_Visualization_and_Characterization_of_Deep_Network_Geometry_and_CVPR_2023_paper.html)). Rolnick and Kording (ICML 2020) recover *weights* from queries using the same region geometry, which is parameter extraction, not algorithm recovery ([PMLR](https://proceedings.mlr.press/v119/rolnick20a.html)).

Classic rule extraction is mature but a poor fit. The pedagogical/decompositional/eclectic taxonomy and methods such as TREPAN, DeepRED and ECLAIRE produce **approximate, classification-oriented** rule sets ([El Mekkaoui et al. review](https://arxiv.org/pdf/2312.12878); [ECLAIRE](https://arxiv.org/pdf/2111.12628)). The implementations are stale. `ruleex` was last released in 2019 and needs TensorFlow plus optional R ([PyPI](https://pypi.org/project/ruleex/)). REMIX needs Python 3.5–3.8 and R ([GitHub](https://github.com/mateoespinosa/remix)). Neither installs on Python 3.13. Their modern equivalent is a scikit-learn tree fitted to dense samples of the network, which is TREPAN-lite and is what REMIX's PedC5.0 does with C5.0.

## Symbolic regression and KANs snap formulas, not trained-MLP constants

**PySR** is the strongest symbolic-regression baseline because its built-in operators cover every task here in closed form. They include `abs`, `max`, `min`, `cond` (x > 0 ? y : 0), `greater`, `logical_and/or`, `sign` and `relu` ([PySR operators](https://huggingface.co/spaces/MilesCranmer/PySR/raw/7763215ce65b491b19742a7cacce36735dd3cd95/docs/operators.md)). Median of 3 is `max(min(a,b), min(max(a,b),c))`, the window is `greater(0.5, abs(x))`, and the tax rule is a sum of `relu(x − t)` terms. Its loss-versus-complexity selection fits constants rather than rounding them, so whether it returns 0.198 or 0.2 is an empirical question. SRBench 2025 runs 25 methods, recommends its roster for new baselines, and finds no single dominant algorithm ([SRBench](https://cavalab.org/srbench); [arXiv 2505.03977](https://arxiv.org/abs/2505.03977)). AI Feynman, which MIPS borrows its brute-force search from, supports only Linux and macOS and needs gfortran ([docs](https://ai-feynman.readthedocs.io/en/latest/installation.html)). pyoperon's PyPI build lags its GitHub wheels ([PyPI](https://pypi.org/project/pyoperon)).

**KAN symbolification** (ICLR 2025) is the closest published analogue to snapping. It sparsifies and prunes the network, fits each 1-D edge to c·f(a·x+b)+d from a library chosen by R², and refits only the affine constants. It treats machine-precision loss as the sign that the formula is right ([KAN paper](https://arxiv.org/html/2404.19756); [ICLR](https://iclr.cc/virtual/2025/poster/29784)). The default library has `abs` and `sgn`, but `relu` is commented out ([pykan utils.py](https://raw.githubusercontent.com/KindXiaoming/pykan/master/kan/utils.py)). That suits |a−b| and max but not thresholds. KAN snaps *function forms* inside a *different model class*, so it cannot run on the repo's MLP weights. It also does not round (a, b, c, d) to intended values by default. Later work warns that trained KAN activations often learn "pathological decompositions" with no interpretable counterpart ([S2KAN, arXiv 2512.07875](https://arxiv.org/html/2512.07875v1)). The same risk applies to any post-hoc snapping: a network's internals need not mirror the intended program even when its behaviour does.

The repo's "the snapped program beats the network on the true task" result has one strong outcome precedent. **Cranmer et al. (NeurIPS 2020)** report that symbolic expressions extracted from a GNN "generalized to out-of-distribution data better than the GNN itself" ([NeurIPS](https://proceedings.neurips.cc/paper/2020/hash/c9f2f917078bd2db12f23c3b413d9cba-Abstract.html)). They used symbolic regression, not weight snapping. MIPS does not test out-of-distribution generalization. Generic quantization-as-regularizer work is mixed: QT-DoG reports gains, and a 2025 study finds standard QAT can hurt OOD ([arXiv 2410.06020](https://arxiv.org/html/2410.06020v1); [arXiv 2509.00859](https://arxiv.org/html/2509.00859v1)). It says nothing about recovering exact algorithms. The OOD advantage on piecewise tasks is also expected rather than surprising. A slope error of 0.2% or a breakpoint at 0.497 instead of 0.5 grows with input magnitude, and an exact formula has neither. That should be framed as confirmation, not discovery.

## No published benchmark pits branch code against straight-line MLP C

No paper was found that compiles a trained ReLU MLP into branching C and benchmarks CPU inference against the straight-line matrix implementation. The exact-tree papers report interpretability or verification speedups, not inference timings ([Chang et al.](https://arxiv.org/abs/2304.06049)). "Compile the network to logic for speed" lives on FPGAs instead. **LogicNets** and **NeuraLUT** turn quantized neurons or whole sub-networks into truth tables. They require networks trained for it, and LUT size grows exponentially with fan-in ([LogicNets](https://arxiv.org/pdf/2004.03021); [NeuraLUT](https://arxiv.org/pdf/2403.00849)). The off-the-shelf C generators split by model type. TL2cgen, m2cgen and emlearn compile *trees* to C ([TL2cgen](https://tl2cgen.readthedocs.io); [emlearn](https://pypi.org/project/emlearn/0.12.0/)). onnx2c, TVM's C target and emx-onnx-cgen compile *networks* to straight-line C. onnx2c lists no loop unrolling or constant folding ([onnx2c](https://github.com/kraiskil/onnx2c)), so for a 2→8→1 net a hand-unrolled `static const` version compiled at -O3 is the stronger and fairer baseline. One hypothesis, not a sourced finding, should shape the benchmark design: a tiny dense MLP is a few dozen fused multiply-adds with no branches. Decompiled branch code may lose on random inputs through branch misprediction unless the program is much shorter or compiles to branchless `fmax`/`fmin`. The repo's planned "branch-unpredictable input set" already covers this.

## Five baselines that run on a CPU-only Windows laptop

The baselines below were chosen to isolate the three things the repo claims: search quality (does the program have the right *form*?), snapping (are its *constants* intended?) and the value of reading weights (does the *dump* help the LLM?). Each output should be converted into the repo's program language so the same checker and the same `cgen` grade and compile it. The install notes come from the cited pages. None of these were tested on Python 3.13/Windows during this research, so treat version claims as things to check.

pykan is a reasonable optional sixth. Its pinned `torch==2.2.2` and `numpy==1.24.4` ([pykan](https://github.com/KindXiaoming/pykan)) predate Python 3.13 wheels (an inference from those versions, not checked), so it belongs in a separate Python 3.11/3.12 venv. It also answers a different question: whether a model class built for symbolification recovers these tasks when trained on the same data. gplearn is pure pip ([docs](https://gplearn.readthedocs.io/en/stable/installation.html)) but needs custom `abs`/`max`/`greater` functions, and its compatibility with recent scikit-learn is unverified. The MIPS code is RNN-specific and serves as a cited precedent, not a drop-in. ruleex, REMIX and AI Feynman do not run natively on this setup.

## Claim the combination, not the components

The table separates what prior work already does from what the searches did not find. "Not found" means not found in the targeted searches of four research threads behind this report. It is not proof of absence. Hobbyist experiments in which someone pasted a small network's weights into ChatGPT or Claude may exist on blogs, LessWrong or GitHub without surfacing.

| CPU speed of decompiled branch C vs straight-line MLP C | **Not found** | Exact-tree papers report verification speedups only; LUT work is FPGA-only |

The repo's own numbers should be framed modestly. In-sample was **21 of 21** and held-out **5 of 6** ([README](../README.md)). That is about 27 models, against MIPS's 62 tasks. The held-out miss is informative rather than embarrassing. On tax brackets, the deterministic tool produced a valid but blurred `max(0.12x, 0.2x − 1.68, 0.4x − 17.68)`, while Claude snapped it to rates 0.1/0.2/0.4 with brackets at 20 and 80. That is direct evidence that semantic, non-integer snapping is where the LLM adds something the mechanical heuristics do not. It is also the one capability MIPS-style integer rounding cannot reach. A defensible one-sentence positioning for the README is: *"Like MIPS, nndc automatically distills small trained ReLU networks into Python with snapped constants; unlike it, nndc targets feed-forward MLPs on real-valued piecewise tasks, has a task-blind LLM agent refactor a per-neuron code dump into a program with non-integer intended constants, accepts a program only by comparison with the network itself, and tests how much of that agent's work a frozen deterministic tool can reproduce on held-out models — a combination we did not find in prior work."* The speed claim should wait until step 5 has measured it.

## Conclusion

The literature has two halves that have not been joined. Weight-reading decompilers (MIPS, D-RASP, Weights to Code) are deterministic pipelines that snap only to integers or to library primitives. LLM interpreters (FIND, MAIA, LLM-SR) never see weights and fit constants rather than choosing them. The repo's tax-bracket result suggests why joining them matters: choosing 0.2 over 0.198 is a judgment about *intent*, and intent is what a language model brings and a rounding threshold lacks. Baseline 5, the input/output-only agent, is therefore the most important experiment to add. If Claude does as well without the dump, the contribution shrinks to "LLM plus checker". If it does worse, the repo has the first evidence that reading weights as code helps an LLM recover intended programs.

Two further results would strengthen the paper more than any extra task. The first is showing that PySR plus the repo's snapping pass does or does not close the tax-bracket gap, which separates search from snapping. The second is reporting the branch-versus-straight-line timing honestly even if straight-line wins. The speed niche is unoccupied, and a negative result there is still the first published one.
