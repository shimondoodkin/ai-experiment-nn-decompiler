# ast4: keep the smallest kink-merge program

Status: approved in chat ("ok do the real fix"), 2026-10-30. Follows `2026-10-29-ast3-tanh-design.md`.

## Why

`ast3` was larger than `ast2` on 5 of 45 sigmoid runs (`CONCLUSIONS.md`, "Tanh nets and `ast3`"). A spike on
2026-10-30 found the mechanism:
- **The route stops at the first program that passes.** Its order is: fewest lines first, merge offset 0.02 before
  0.1, then snap levels coarsest first (5%, 2%, 1%, 0.5%, 0).
- **`ast3` rounds more.** Its position window is twice the old one on diagonal lines, and its constant may move by
  `tol·R`. So at the line count where `ast2` passed, `ast3`'s candidates fail, and the route goes on to a finer level
  (absdiff) or more lines (neareq seed 5: 7 lines instead of 4).
- **Passing is not monotone in the snap level.** On neareq seed 4, one 4-line candidate passes at 5% and fails at 2%.
  So "first pass, coarsest first" is partly luck.

**The spike** (scratchpad, then copied to `experiments/spikes/ast4_snap_variants/`):
- It built every candidate: m = 1–8, both merge offsets, all 5 snap levels, and 4 snap variants.
- Each variant is a position window (`ast3`'s line range, or `ast2`'s max span) plus a constant (rounded, or not).
- It checked every candidate, on the 30 one-layer sigmoid formula nets of seeds 0–5.
- Its `ast3` policy reproduced the committed `ast3` sizes on all 30.
- **Policies, against `ast2`** (tool size = smaller of the route and the best other route):

  | policy | smaller | same | larger |
  |---|---|---|---|
  | `ast3` as committed | 3 | 22 | 5 |
  | only fixes 1–2 | 1 | 29 | 0 |
  | 4 variants per level, smallest | 4 | 26 | 0 |
  | **smallest at the first line count that passes** | **5** | **25** | **0** |

  The last policy equals the smallest passing program anywhere in the grid on every one of the 30 nets.

## Goals

1. **A new tool version, `ast4`** (`ast4.py`, `ast4_trace.json`, `counterexamples_ast4.json`). It is `ast3` with one
   change, in the kink-merge route only:
   - For m = 1, 2, …, 8: build every candidate for this m. That is both merge offsets × the 5 snap levels × 4
     variants (position window line-range or max-span; constant rounded or unrounded). Check each one.
   - If any passes, the route returns the passing candidate with the fewest nodes. Ties go to exact over snap, then
     the rounded constant, then the line-range window, then the coarser level, then offset 0.02.
   - If none passes, go to m + 1.
   - The trace's winner records the variant (`window`, `round_const`) as well as `off`, `m`, `tol`.

   Every other route, the tanh rewrite and the checker are as in `ast3`. `ast3` stays runnable and unchanged.
2. **Development set:** every existing sigmoid run (seeds 0–8, including `ast3`'s held-out 6–8) and every existing
   tanh run (all 30). `ast4` runs on all of them.
3. **Freeze**, then **fresh held-out nets**, built after the freeze and run once:
   - sigmoid seeds 9–11 of xor, window, neareq, absdiff and tax (15 nets);
   - tanh seed 3 of the same five tasks (5 nets).

   They get `formula.py` and no agents. The frozen `ast3` also runs on them, as the comparison.
4. **`heldout.json` per root names `ast4`'s held-out set.** `ast3`'s file is renamed `heldout_ast3.json`.
5. **Report:**
   - the newest tool version is `ast4`;
   - the kink-merge section compares `ast4` with each older version present (`ast2`, `ast3`), by the "worse" rule.
6. **Replacing older files:** if `ast4` is never worse than `ast2` or `ast3` on any run, I propose removing the
   `ast2` and `ast3` files from the runs. That happens in a commit of its own, only after the user agrees.
7. **`CONCLUSIONS.md`:** a short `ast4` part.

## The "worse" rule (unchanged from the `ast3` design)

`ast4` is worse than an older version on one run when:
- the older version passes and `ast4` does not;
- or the older version recovers the formula and `ast4` does not;
- or both pass and `ast4` has more nodes.

## Predictions (written before any tool code)

- **Development, sigmoid seeds 0–5:** against `ast2`, 5 smaller, 25 same, 0 larger on the 30 formula nets, as in the
  spike. Median3 and Iris are unchanged, since the route does not apply.
- **Development overall:** `ast4` is never worse than `ast3` or `ast2` on any run.
- **Held-out (20 nets):** `ast4` passes on all 20. It is no larger than the frozen `ast3` on every one, and smaller on
  at least one neareq or absdiff net.
- **Runtime:** the route makes up to 40 checks per line count. I expect 2–3 minutes per net where it applies.

## Non-goals

- Changing the position windows, the snap levels or the checker: `ast4` only searches over what `ast2` and `ast3`
  already do.
- A cap on the constant's window. The unrounded-constant variant already covers it. The constant is one node either
  way, so rounding it only changes readability, and the tie-break prefers it.
- Agents on the new held-out nets, median3, smooth functions.

## Anti-goals

- Any change to ReLU results (equivalence script: 0 differences) or to `ast3`'s programs.
- Tuning after a held-out result, or building held-out nets before the freeze.
- Removing older files without the user's agreement.

## Constraints

Everything in CLAUDE.md: data commits apart from code commits, no destructive commands on the repo.
